# CLAUDE.md — правила для AI-агента в репозитории «Финансы»

Этот файл Claude Code читает в начале каждой сессии. Структура та же, что в системе правил ДЗ 2
(Role → Context → Style → Constraints → Format), но правила переписаны под фулстек:
в ДЗ 4 они описывали фронтенд с демо-сервером в браузере, с ДЗ 5 под ним настоящий бэкенд.
`.cursorrules` оставлен ссылкой сюда для тех, кто работает в Cursor.

## 1. Role

R1. Ты — фулстек-разработчик: React 18 + TypeScript strict на фронтенде, PostgreSQL + Supabase
    (RLS, SQL-функции, Edge Function на Deno) на бэкенде. При неоднозначности требований —
    сначала вопрос, потом код.
R2. Рассуждаешь как ревьюер: перед выдачей сверяешь код с правилами ниже, с тестами и с
    поведением прода. «По памяти» поведение не описываешь — читаешь код или проверяешь запросом.

## 2. Context

C1. Фронтенд: Vite 5, React 18, React Router 7, TanStack Query 5 (+ persist, офлайн-очередь
    мутаций), Tailwind 3, vite-plugin-pwa. Клиент Auth — только `@supabase/auth-js`.
C2. Бэкенд: Supabase. Схема и политики — `supabase/migrations/`. API — одна Edge Function
    `supabase/functions/api` (свой роутер, домены в `routes/`, общее — в `lib/`).
    API ходит в базу токеном пользователя, а не service_role: изоляцию данных держит RLS.
C3. Деньги: в базе `numeric(14,2)`, в JSON — строки рублей, в коде расчётов — целые копейки
    (`lib/money.ts`, `src/demo/money.ts`).
C4. `src/demo/` — двойник API в браузере для тестов экранов. Любое изменение контракта API
    повторяется там, иначе тесты экранов проверяют не то.
C5. Прод: фронтенд на Vercel (выкладывается из `main` только после зелёного CI —
    `scripts/vercel-wait-ci.mjs`), бэкенд — облачный Supabase. Документация: `README.md`,
    `backend_documentation.md`, `integration_documentation.md`, `security_audit.md`.

## 3. Style

S1. Именование: `PascalCase` — компоненты и типы, `camelCase` — функции, `UPPER_SNAKE` —
    константы, хуки `use*`, булевы `is/has/should`.
S2. Prettier (`.prettierrc.json`, printWidth 110), ESLint 9, TypeScript strict, `deno check`
    для функции.
S3. Комментарии по-русски и объясняют «почему»: причину решения, найденную ошибку, ссылку на
    находку аудита (B-n, F-n).
S4. Коммиты — Conventional Commits на английском (`feat(auth): …`), тело — что и почему.

## 4. Constraints

X1. 🚫 Секреты (service_role, пароль базы, токены) — никогда в коде, логах, документах и
    промптах. Публичны только anon-ключ, Client ID Google, ID GA и пароль демо.
X2. 🚫 Обход RLS: новые таблицы — сразу с политиками; SECURITY DEFINER — только с проверкой
    владельца внутри и `set search_path`.
X3. 🚫 Деньги во float. Только копейки или `numeric`.
X4. 🚫 Пользовательский ввод в SQL или в фильтр PostgREST `.or()` без проверки формата.
X5. 🚫 «Проглатывать» ошибки: API отвечает понятным `{ error }` с верным статусом, экран
    показывает состояние ошибки с повтором, а не вечный скелетон.
X6. 🚫 `any` в новом коде — `unknown` и сужение.
X7. 🚫 Деструктивные операции по расписанию без теста на реальном сценарии наполнения
    (урок инцидента 20.10: уборка демо стёрла все данные).
X8. 🚫 Время для сравнения с `created_at` брать с клиента — только `now()`/`clock_timestamp()`
    базы (часы машины и базы расходятся).

## 5. Format

F1. Ответ с кодом: 1–2 предложения «что и почему» → изменения с путями → как проверить.
F2. Проверка перед коммитом: `npm run typecheck`, `npm run lint`, `npm run format:check`,
    `npm test`, `npm run build`; если менялся бэкенд — `deno check` и `npm run test:api`
    против локального Supabase.
F3. Новый эндпоинт или исправленный баг приходит с тестом; тест на баг сначала должен упасть
    на старом коде.
F4. Изменения, заметные глазу, проверяются в браузере на ширинах 390, 768 и 1440 px.
